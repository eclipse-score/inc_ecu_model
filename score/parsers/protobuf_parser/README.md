# Protobuf Parser

This directory provides a two-phase pipeline from Bazel-produced Protobuf
`proto3` descriptors to SCORE ECU model data types:

1. Convert a `FileDescriptorSet` into Deployment data type
     definitions.
2. Resolve field references by Protobuf type name after all definitions have
     been registered.

## Module Responsibilities

- [`api.py`](api.py)
    Defines the pipeline-facing `ProtobufToDataTypeParser`, which registers declarations
    and resolves references into a mutable mapping.
- [`transformer.py`](transformer.py)
    Converts descriptors into SCORE data type instances and collects the
    context required for subsequent reference resolution.
- [`option_decoder.py`](option_decoder.py)
    Decodes explicitly set standard and custom Protobuf options.
- [`common.py`](common.py)
    Defines types, errors, and naming helpers shared by the transformer, resolver, and
    option decoder.
- [`resolver.py`](resolver.py)
    Replaces deferred references with concrete data type definitions using the
    symbol table and namespace.

## Bazel Integration

For model consumers, use [`ecu_model_parse`](../../orchestrator/ecu_model_parse.bzl). Bazel owns Protobuf compilation
and import resolution; the orchestrator consumes the descriptor sets and writes the whole model registry:

```text
proto_library targets
    -> ProtoInfo.transitive_descriptor_sets
    -> ecu_model_parse Bazel action
    -> run_load_dispatch Python executable
    -> ProtobufToDataTypeParser descriptor-set entry point
    -> serialized ModelRegistry
```

This boundary delegates physical path handling to the standard Protobuf Bazel
rules. It supports imports from workspace and external repositories, Google
well-known Protobuf types, generated proto files, and targets using
`import_prefix` or `strip_import_prefix`. The Python parser sees stable logical
file names from the descriptors and does not need to interpret Bazel sandbox
paths or `_virtual_imports` directories.

Inputs should be provided as targets exposing `ProtoInfo`. These are normally direct `proto_library` targets or the
`*_proto` targets currently generated by `spp_package3`. Raw `.proto` files used as test data need a `proto_library`
wrapper before they can use this integration.

For example, an imported proto and its consumer can be declared as follows:

```starlark
load("//score/orchestrator:ecu_model_parse.bzl", "ecu_model_parse")

proto_library(
    name = "input_vehicle_data_proto",
    srcs = ["input_vehicle_data_pod.proto"],
)

proto_library(
    name = "activation_decision_input_proto",
    srcs = ["activation_decision_input_data_pod.proto"],
    deps = [
        ":input_vehicle_data_proto",
    ],
)

ecu_model_parse(
    name = "activation_decision_model",
    protobuf_deps = [":activation_decision_input_proto"],
)
```

`ecu_model_parse` constrains `protobuf_deps` to targets providing `ProtoInfo`, collects their
`transitive_descriptor_sets`, declares those files as action inputs, and passes their paths to the executable. It does
not reconstruct `--proto_path` from `File.path`, external repository names, or `_virtual_imports` paths.

The orchestrator forwards the Bazel-provided descriptor artifact paths to `ProtobufToDataTypeParser.parse()`. The parser
loads and combines those artifacts into a `FileDescriptorSet` before model conversion. Bazel `depset` performs
descriptor-artifact deduplication.

The separate `proto_parser_example` rule and `proto_parser_runner` are test-only fixtures; they serialize a datatype
mapping rather than the whole registry. The Franca `franca_transformer_runner` serves the same test-only purpose.

If source comments or precise source locations become model requirements, the
Bazel integration must generate descriptors with `--include_source_info`.
Otherwise, the descriptor sets already exposed through `ProtoInfo` are the
preferred input because they avoid duplicating Bazel's import-path logic.

The parser uses built-in `PrimitiveDataType` values for Protobuf primitive
fields; primitives are not declarations and therefore are not registry entries.
It supports messages, enums, nested messages, nested enums, `repeated` fields,
map fields, and `oneof` fields. Nested declarations are registered with their
complete hierarchy; for example, `package.Outer.Inner` has the data type key
`package.Outer.Inner`.

Explicitly set standard and custom Protobuf options are decoded into a
definition or field's `description` and `deployment_properties`. Standard
options use their complete field names as property keys, for example
`google.protobuf.FieldOptions.deprecated`. Message-valued custom options are
flattened so each ordinary leaf value uses its complete option path as a key,
for example `integration.deployment.field_deployment.transport`. Description
values are promoted into textual descriptions, and `max_count` is used for a
repeated field's dimension; neither is retained in `deployment_properties`.

### Target Option-Decoding Design

The target implementation keeps standard and custom option decoding on separate
paths. Standard option fields are read directly from the original static
`descriptor_pb2.*Options` message. This preserves the standard runtime's
semantics and considers only explicitly set non-extension fields.

Custom extension fields are decoded through a private `DescriptorPool` that
contains `google/protobuf/descriptor.proto` and the complete
compiler-produced `FileDescriptorSet`. A dynamic matching
`google.protobuf.*Options` class reparses the original option-message bytes and
contributes only explicitly set extension fields. The two normalized dictionaries
are merged only after both decoding paths complete.

An earlier implementation added a synthetic `protobuf_option_projection.proto`
descriptor to the private pool. That accidentally reserved a legitimate user
file name and caused custom-option schemas with that name to fail. The
custom-option path must therefore not add synthetic projection descriptors or
reserve user-visible file, package, or message names.

## Reference Resolution

Parsing does not immediately bind user-defined field types. After every
definition has been indexed by data type key, the resolver looks up the fully
qualified type name recorded in the descriptor.

The `ProtobufToDataTypeParser.parse()` input contract requires paths to complete
`FileDescriptorSet` artifacts generated by successfully compiling with
`protoc`. `protoc` validates
imports, dependency availability, and type visibility; the resolver does not
repeat those checks.

`resolve_references()` returns a list of `ProtoResolverIssue` instances instead of
raising a parsing error directly. Callers must check that list. After successful
resolution, field types, array element types, and map key/value types point to
their concrete definitions in the definition mapping.

`ProtobufToDataTypeParser.parse()` performs this check and raises
`ProtoResolverError` when reference resolution produces issues.

## Limitations And Error Handling

- Only `proto3` is supported; a `proto2` descriptor raises `ProtoTransformerError`.
- Conflicting generated type definitions raise `ProtoTransformerError`.
- `transformed_result.definitions_by_key` contains every generated definition before the
    resolver runs; otherwise it returns an `unresolved_type` issue.
- Hand-built or incomplete `FileDescriptorSet` instances are outside the
    resolver's supported input contract.
